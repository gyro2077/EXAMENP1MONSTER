REQUERIMIENTO PARA AGENTE DE DESARROLLO
SERVIDOR FEDERACIÓN DE FÚTBOL - SOAP JAVA + POSTGRESQL + MVC + PAYARA

Contexto general
----------------
Se necesita implementar únicamente el servidor de la aplicación "Federación de Fútbol".
Este servidor será consumido posteriormente por otro sistema llamado "TicketPremium".
El servidor debe exponer Web Services SOAP en Java, usar PostgreSQL como base de datos,
respetar una arquitectura MVC por capas y desplegarse en Payara.

No implementar REST.
No implementar la aplicación cliente TicketPremium.
No implementar facturación, IVA, compras ni reporte de ventas en este servidor.
Este servidor solo gestiona partidos, localidades, precios, disponibilidad y decremento de disponibilidad.

Requerimientos funcionales del servidor
---------------------------------------

RF-SERV-01: Implementar tabla PARTIDO_FUTBOL
--------------------------------------------
La tabla debe almacenar los partidos de fútbol.

Campos:
- CODIGO: identificador del partido.
- EQUIPO_LOCAL: nombre del equipo local.
- EQUIPO_VISITA: nombre del equipo visitante.
- FECHA: fecha y hora del partido.
- LUGAR: lugar donde se realizará el partido.

Script SQL recomendado:

CREATE TABLE partido_futbol (
    codigo SERIAL PRIMARY KEY,
    equipo_local VARCHAR(100) NOT NULL,
    equipo_visita VARCHAR(100) NOT NULL,
    fecha TIMESTAMP NOT NULL,
    lugar VARCHAR(150) NOT NULL
);

Criterio de aceptación:
- La tabla existe.
- Tiene al menos 5 registros de prueba.
- Permite consultar partidos cuya fecha sea mayor o igual a la fecha actual.

RF-SERV-02: Implementar tabla LOCALIDAD_PARTIDO
-----------------------------------------------
La tabla debe almacenar las localidades disponibles para cada partido.

Campos:
- ID: identificador interno.
- CODIGO_PARTIDO: referencia al partido.
- CODIGO_LOCALIDAD: código de localidad, por ejemplo GENERAL, TRIBUNA, PALCO.
- DISPONIBILIDAD: número de boletos disponibles.
- PRECIO: precio unitario de la localidad.

Script SQL recomendado:

CREATE TABLE localidad_partido (
    id SERIAL PRIMARY KEY,
    codigo_partido INTEGER NOT NULL,
    codigo_localidad VARCHAR(50) NOT NULL,
    disponibilidad INTEGER NOT NULL,
    precio NUMERIC(10,2) NOT NULL,

    CONSTRAINT fk_localidad_partido
        FOREIGN KEY (codigo_partido)
        REFERENCES partido_futbol(codigo),

    CONSTRAINT uk_partido_localidad
        UNIQUE (codigo_partido, codigo_localidad),

    CONSTRAINT chk_disponibilidad
        CHECK (disponibilidad >= 0),

    CONSTRAINT chk_precio
        CHECK (precio >= 0)
);

Relación:
PARTIDO_FUTBOL 1 ---- N LOCALIDAD_PARTIDO

Criterio de aceptación:
- La tabla existe.
- Está relacionada con PARTIDO_FUTBOL.
- Tiene al menos 20 registros de prueba.
- No permite disponibilidad negativa.
- No permite precio negativo.
- No permite duplicar la misma localidad para el mismo partido.

RF-SERV-03: Web Service SOAP para listar partidos disponibles
-------------------------------------------------------------
Debe existir una operación SOAP que devuelva los partidos disponibles.

Nombre de operación:
listarPartidosDisponibles()

Regla de negocio:
Un partido está disponible si:
fecha >= CURRENT_TIMESTAMP

Consulta lógica:
SELECT *
FROM partido_futbol
WHERE fecha >= CURRENT_TIMESTAMP
ORDER BY fecha ASC;

Debe retornar una lista de PartidoDTO con:
- codigo
- equipoLocal
- equipoVisita
- fecha
- lugar

Criterio de aceptación:
- El método existe en el WSDL.
- Retorna solo partidos actuales o futuros.
- No retorna partidos pasados.
- Ordena los partidos por fecha ascendente.

RF-SERV-04: Web Service SOAP para listar localidades disponibles
----------------------------------------------------------------
Debe existir una operación SOAP que reciba el código del partido y devuelva sus localidades disponibles.

Nombre de operación:
listarLocalidadesDisponibles(Integer codigoPartido)

Regla de negocio:
Una localidad está disponible si:
disponibilidad > 0

Consulta lógica:
SELECT *
FROM localidad_partido
WHERE codigo_partido = ?
AND disponibilidad > 0
ORDER BY codigo_localidad ASC;

Debe retornar una lista de LocalidadDTO con:
- codigoLocalidad
- disponibilidad
- precio

Validaciones:
- El código del partido no debe ser nulo.
- Debe devolver solo localidades con disponibilidad mayor a cero.
- No debe devolver localidades agotadas.

Criterio de aceptación:
- El método existe en el WSDL.
- Recibe como parámetro el código del partido.
- Devuelve únicamente localidades disponibles.
- Incluye el precio de cada localidad.

RF-SERV-05: Web Service SOAP para decrementar disponibilidad
------------------------------------------------------------
Debe existir una operación SOAP que reduzca la disponibilidad de una localidad.

Nombre de operación:
decrementarDisponibilidad(Integer codigoPartido, String codigoLocalidad, Integer cantidad)

Parámetros:
- codigoPartido
- codigoLocalidad
- cantidad

Reglas de negocio:
- El partido debe existir.
- La localidad debe existir para ese partido.
- La cantidad debe ser mayor que cero.
- Debe existir disponibilidad suficiente.
- La disponibilidad nunca puede quedar negativa.
- La operación debe ser transaccional.

Respuesta recomendada:
ResultadoOperacionDTO

Campos de ResultadoOperacionDTO:
- exitoso: Boolean
- mensaje: String
- disponibilidadActual: Integer

Mensajes sugeridos:
- "Datos incompletos."
- "La cantidad debe ser mayor a cero."
- "El partido no existe."
- "La localidad no existe para el partido seleccionado."
- "No existe disponibilidad suficiente."
- "Disponibilidad actualizada correctamente."

Control de concurrencia recomendado:
Usar bloqueo pesimista con JPA:

setLockMode(LockModeType.PESSIMISTIC_WRITE)

O lógica equivalente en SQL:

SELECT *
FROM localidad_partido
WHERE codigo_partido = ?
AND codigo_localidad = ?
FOR UPDATE;

Luego actualizar la disponibilidad.

Criterio de aceptación:
- El método existe en el WSDL.
- Descuenta correctamente la cantidad solicitada.
- No permite ventas con disponibilidad insuficiente.
- No permite disponibilidad negativa.
- Retorna mensaje claro de éxito o error.
- Maneja concurrencia para evitar sobreventa.

Repositories requeridos
-----------------------

PartidoRepository.java
Responsabilidades:
- buscarPartidosDisponibles()
- buscarPorCodigo(Integer codigo)

Consulta principal:
SELECT p FROM PartidoFutbol p
WHERE p.fecha >= :fechaActual
ORDER BY p.fecha ASC

LocalidadRepository.java
Responsabilidades:
- buscarLocalidadesDisponibles(Integer codigoPartido)
- buscarParaActualizar(Integer codigoPartido, String codigoLocalidad)
- actualizar(LocalidadPartido localidad)

Consulta para localidades disponibles:
SELECT l FROM LocalidadPartido l
WHERE l.partido.codigo = :codigoPartido
AND l.disponibilidad > 0
ORDER BY l.codigoLocalidad ASC

Consulta para actualización:
Debe usar LockModeType.PESSIMISTIC_WRITE para evitar sobreventa.

- Cambiar imports de jakarta a javax

Criterios finales de aceptación
-------------------------------

El servidor se considera terminado si cumple:

1. Existe una base PostgreSQL llamada federacion_db.
2. Existe la tabla partido_futbol.
3. Existe la tabla localidad_partido.
4. La relación partido-localidad está correctamente implementada.
5. Hay al menos 5 partidos de prueba.
6. Hay al menos 20 localidades de prueba.
7. El proyecto compila como WAR.
8. El proyecto despliega correctamente en Payara.
9. Existe el WSDL del servicio SOAP.
10. El WSDL muestra las operaciones:
    - listarPartidosDisponibles
    - listarLocalidadesDisponibles
    - decrementarDisponibilidad
11. listarPartidosDisponibles retorna solo partidos con fecha actual o futura.
12. listarLocalidadesDisponibles retorna solo localidades con disponibilidad mayor a cero.
13. decrementarDisponibilidad descuenta correctamente.
14. decrementarDisponibilidad no permite disponibilidad negativa.
15. El código respeta separación MVC por capas:
    - model
    - dto
    - repository
    - service
    - soap/controller
